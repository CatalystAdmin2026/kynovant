# AI-Assisted Program Generator UX Specification

Status: Draft for approval  
Owner: Kynovant HQ  
Scope: Coach-facing AI-assisted generation of draft Programs and workout Blueprints  
Last updated: 2026-08-03

---

## 1. Product Intent

The AI-assisted Program Generator helps a coach turn a structured coaching brief into a complete multi-week draft Program. The system may draft Program weeks, training days, workout Blueprints, exercises, prescriptions, progression notes, and rationale, but it must never publish, assign, or replace anything without explicit coach approval.

The generator extends the existing manual workflow. Coaches can still create Programs and Blueprints manually. Generated output enters HQ as a draft review surface first, then becomes ordinary Kynovant Program and Blueprint records only after approval.

The experience must answer:

- What did Kynovant generate?
- Why did it make those choices?
- Is the draft structurally safe enough to approve?
- What must the coach review or fix first?
- What will be created if the coach approves?

---

## 2. Product Language

Use these terms consistently:

| Term | Meaning |
|---|---|
| Program | A multi-week plan assigned or assignable to a client |
| Blueprint | A reusable single-workout template |
| Program Brief | Coach-authored structured input for generation |
| Generated Draft | Temporary review object, not yet a real Program |
| Kynovant Insights | Deterministic audit layer for Program and Blueprint quality |
| Warning | Coach should review before approval; may still approve |
| Blocker | Must be resolved before approval |

Do not expose internal terms such as PIL, LLM, prompt, tokens, chain, or model provider in coach-facing UI. Version/audit metadata may show "Generated by Kynovant" plus technical metadata in an audit drawer.

---

## 3. Core Safety Rules

1. No autonomous publishing.
2. No autonomous assignment.
3. No silent exercise creation.
4. No medical or injury diagnosis.
5. No hidden substitutions.
6. No generated draft can become a Program until the coach explicitly approves.
7. Kynovant Insights findings must be visible before approval.
8. Blockers must prevent approval.
9. Warnings must be reviewable and overridable by coach judgment.
10. Manual Program Builder and Blueprint Editor remain available.

---

## 4. Existing Product Surfaces To Reuse

The MVP should reuse these existing patterns instead of inventing a separate product:

- HQ dark premium shell
- Existing Program Builder concepts: weeks, day slots, Blueprint assignment
- Existing Blueprint Editor concepts: sections, prescriptions, techniques, exercise picker
- Existing Kynovant Insights hierarchy: status chips, Highest Priority, finding cards, evidence disclosure
- Existing UI primitives: `Button`, `Badge`, `Input`, `Textarea`, `Select`, `Modal`, `Tabs`, `StatusChip`, `Table` where appropriate
- Existing language split: Program = multi-week, Blueprint = single workout

## 5. Entry Points

### 5.1 Client Workspace Entry

Location: `/hq/clients/[clientId]`

Primary placement:

- Program area, near Assign / Replace Program actions
- CTA label: `Generate Program`
- Secondary text: `Draft a multi-week plan from this client's profile and your brief.`

Behavior:

- Opens Program Brief flow with client preselected and locked.
- Pulls available client context if it exists: profile, active goal, training profile, nutrition profile, limitations, current program state.
- If client profile is incomplete, show an honest readiness note:
  - `Some client profile fields are missing. You can still generate a draft, but equipment, limitations, or preferences may need manual review.`

Do not:

- Auto-archive current Program.
- Auto-assign generated Program.
- Hide the manual Assign Program flow.

### 5.2 Programs Page Entry

Location: `/hq/programs`

Primary placement:

- Header action group beside `New Program`
- CTA label: `Generate Program`

Behavior:

- Opens Program Brief flow without a client locked.
- Client field is optional for a library Program draft.
- If no client is selected, generated Program is draft-only and cannot be assigned during approval until a client is chosen.

### 5.3 Optional Empty-State CTA

Locations:

- Empty Programs page
- Client workspace with no active Program
- Get Started checklist, if still relevant

CTA label:

- `Generate First Program`

Empty state copy:

`Start from a coach brief. Kynovant will draft the Program and Blueprints, then you review every detail before anything is created.`

## 6. Program Brief Screen

Purpose: collect structured intent from the coach before generation.

Presentation:

- Full-screen HQ route or large modal: `/hq/programs/generate`
- If launched from client workspace, URL may include `?clientId=...`
- Dark premium surface, two-column layout on desktop:
  - Left: form sections
  - Right: client context, readiness, and generation summary
- Sticky footer:
  - `Cancel`
  - `Save Brief Draft` (post-launch)
  - `Generate Draft`

### 6.1 Form Sections

#### A. Client

Fields:

- Client selector
- Client context card if selected
- Active goal summary if available
- Current Program status if available

States:

- Selected client
- No client selected
- Client profile incomplete

MVP:

- Client selector and read-only context summary

Post-launch:

- Brief prefill from client profile
- Client readiness scoring
- Compare against current Program

#### B. Goal

Fields:

- Primary goal select:
  - Fat loss
  - Muscle growth
  - Body recomposition
  - Athletic performance
  - Lifestyle
  - Competition prep
  - Executive performance
- Goal detail textarea
- Time horizon note

Validation:

- Primary goal required.
- Goal detail recommended but not required.

#### C. Program Structure

Fields:

- Weeks: number input or stepper
- Days per week: segmented control or stepper
- Preferred split:
  - Full body
  - Upper / lower
  - Push / pull / legs
  - Body part split
  - Hybrid
  - Coach decides
- Experience:
  - Beginner
  - Intermediate
  - Advanced
  - Competitive
  - Mixed

Validation:

- Weeks required.
- Days per week required.
- Experience required.

MVP constraints:

- Weeks: 1-16
- Days per week: 1-7

#### D. Muscle Priorities

Fields:

- Multi-select muscle groups
- Priority order
- Optional emphasis notes

UI:

- Compact tag selector with drag handles for priority order.

MVP:

- Multi-select only.

Post-launch:

- Ordered priorities
- Auto-warning when priorities conflict with days/session duration

#### E. Equipment

Fields:

- Equipment access:
  - Commercial gym
  - Home gym
  - Dumbbells only
  - Bands only
  - Bodyweight
  - Custom
- Available equipment text area

MVP:

- Select plus freeform notes.

Post-launch:

- Structured equipment inventory tied to Exercise Library filters.

#### F. Limitations

Fields:

- Limitations / injuries freeform
- Movement restrictions
- Coach notes

Safety copy:

`Use coaching judgment for limitations. Kynovant can avoid listed movements, but it does not diagnose injuries or provide medical advice.`

MVP:

- Freeform limitation text passed into generation and shown during review.

Post-launch:

- Structured limitation mapping to exercise contraindication data.

#### G. Excluded Exercises

Fields:

- Exercise search multi-select
- Freeform excluded movements

Behavior:

- Selected exercises are hard exclusions.
- Freeform exclusions become generator constraints and review notes.

MVP:

- Exercise ID exclusions using existing Exercise Library search.

Post-launch:

- Excluded movement patterns, joints, equipment, or categories.

#### H. Techniques

Fields:

- Allowed set techniques:
  - Straight sets
  - Supersets
  - Trisets
  - Drop sets
  - Rest-pause
  - Myo-reps
  - Tempo work
  - Isometrics
  - Circuits
- Techniques to avoid
- Technique notes

Default:

- Straight sets enabled.
- Advanced techniques disabled unless selected or experience supports them.

#### I. Session Duration

Fields:

- Target minutes per session
- Hard cap toggle
- Warmup included toggle

Validation:

- Target minutes required.
- Hard cap warning if requested volume does not fit.

#### J. Freeform Instructions

Field:

- Large textarea

Placeholder:

`Example: Keep lower body joint stress moderate. Use two upper days and two lower days. Prioritize glutes and upper back. Avoid barbell back squats.`

Display:

- Last section before summary.

### 6.2 Brief Summary Sidebar

Shows:

- Client
- Goal
- Weeks x days per week
- Split
- Experience
- Equipment
- Limitations present / none
- Exclusions count
- Estimated generated assets:
  - Program draft
  - Number of weeks
  - Number of training days
  - Number of workout Blueprints

CTA:

- `Generate Draft`

Disabled state:

- Missing required fields

## 7. Generation State

Purpose: show progress honestly without pretending deterministic precision.

Presentation:

- Full-screen interstitial inside generator route.
- Keep coach in context with brief summary collapsed on right.

Progress stages:

1. `Reading the brief`
2. `Selecting training structure`
3. `Drafting workout Blueprints`
4. `Building weekly progression`
5. `Running Kynovant Insights`
6. `Preparing review`

Language:

- Use calm operational language.
- Avoid fake percentages unless backed by job progress.
- Do not say "optimizing" unless Kynovant Insights or a deterministic pass actually runs.

Primary controls:

- `Cancel Generation`

Cancel behavior:

- Confirms if job has started:
  - `Cancel this generation? No Program or Blueprint will be created.`
- Cancels job if backend supports cancellation.
- If cancellation is not supported in MVP, mark UI as `Stopping review` and discard result when it returns.

### 7.1 Safe Failure State

Failure card:

- Title: `Draft could not be generated`
- Body: concise reason if safe to show
- Actions:
  - `Try Again`
  - `Edit Brief`
  - `Back to Programs`

Failure categories:

- Brief validation failed
- Exercise Library coverage insufficient
- Generation service unavailable
- Kynovant Insights audit failed
- Timeout

Rules:

- Never create partial Program/Blueprint records on failure.
- If a partial generated draft exists, it stays internal and is marked failed.

## 8. Draft Review Screen

Purpose: coach reviews generated plan before anything is created.

Route:

- `/hq/programs/generate/[draftId]`

Top-level layout:

- Header: draft name, client, generated status, approval state
- Left/main: weekly calendar and selected day details
- Right/sticky: Kynovant Insights status, blockers, warnings, approval checklist

### 8.1 Header

Elements:

- Draft name
- Client chip or `Library Program`
- Goal chip
- Weeks / days per week
- Generated timestamp
- Validation status:
  - `Ready for review`
  - `Warnings`
  - `Blocked`
  - `Failed`
- Actions:
  - `Edit Brief`
  - `Regenerate Draft`
  - `Discard`

### 8.2 Weekly Calendar

Display:

- Week tabs or horizontal week rail
- Calendar grid with seven columns
- Training days render workout cards
- Rest days render quiet rest cells

Workout/day card:

- Day label
- Blueprint name
- Focus
- Estimated duration
- Exercise count
- Kynovant Insights mini status
- Warning/blocker indicator

Interactions:

- Click day card selects day details.
- Drag/move day available in Editing mode.
- Rest day can become training day only through explicit edit.

### 8.3 Selected Day Detail

Displays:

- Blueprint title
- Focus
- Estimated minutes
- Sections:
  - Warmup
  - Main lift
  - Accessory
  - Conditioning
  - Finisher
  - Cooldown
- Exercises in order
- Prescription:
  - Sets
  - Reps or duration
  - Rest
  - Tempo
  - RPE/RIR
  - Technique
  - Notes
- Grouping indicators for supersets/trisets

Actions:

- `Regenerate Day`
- `Replace Exercise`
- `Edit Prescription`
- `Reorder`
- `Move Day`

### 8.4 Kynovant Insights Findings

Use existing Kynovant Insights hierarchy:

1. Overall status chips
2. Highest Priority
3. Findings list
4. Evidence disclosure
5. Data quality

Draft Review must include:

- Program-level Insights
- Blueprint-level Insights for selected day
- Data quality summary

Finding classification:

| UI Label | Meaning | Approval Impact |
|---|---|---|
| Blocker | Deterministic invalidity or missing required data | Approval disabled |
| Warning | Meaningful risk or imbalance | Approval allowed after acknowledgement |
| Caution | Heuristic concern | Approval allowed |
| Info | Context or optimization opportunity | Approval allowed |

Blocker examples:

- Missing exercise reference
- Empty training day
- Reps minimum greater than maximum
- Required Program week has no day slots
- Exercise excluded by coach appears in draft

Warning examples:

- High weekly volume
- Recovery spacing concern
- Joint stress concentration
- Duration over target
- Movement pattern imbalance

### 8.5 Approval Checklist

Sticky panel checklist:

- Program structure reviewed
- All blockers resolved
- Warnings reviewed
- Excluded exercises respected
- Kynovant Insights reviewed
- Coach approval required

State:

- Blockers unresolved: `Approve` disabled
- Warnings unresolved: `Approve` enabled only after acknowledgement
- Clean: `Approve Draft` enabled

## 9. Editing UX

Editing occurs inside Draft Review. Edits affect the generated draft only until approval.

### 9.1 Regenerate One Day

Entry:

- Day detail action: `Regenerate Day`

Modal:

- Shows current day summary
- Optional instruction textarea:
  - `Make this lower stress on knees`
  - `Keep the same focus but shorten to 45 minutes`
- Constraint checkboxes:
  - Preserve day focus
  - Preserve duration target
  - Preserve exercise exclusions

Result:

- Replaces that day's draft Blueprint only.
- Runs Blueprint Insights again.
- Updates Program Insights if day changes affect weekly structure.

MVP:

- Regenerate day as a new draft Blueprint version.

Post-launch:

- Show diff before accepting regenerated day.

### 9.2 Replace One Exercise

Entry:

- Exercise row action: `Replace`

Panel:

- Exercise search
- Suggested substitutions if available from existing relation data
- Filters:
  - Same primary muscle
  - Same movement pattern
  - Lower fatigue
  - Equipment compatible

MVP:

- Manual exercise picker using Exercise Library search.
- Coach chooses replacement.
- Prescription copied where compatible.

Post-launch:

- AI-suggested replacement options with rationale.

### 9.3 Edit Prescription

Entry:

- Exercise row action: `Edit`

Fields:

- Sets
- Reps min/max
- Duration
- Rest
- Tempo
- RPE
- RIR
- Technique
- Coach notes

Validation:

- Same validation as Blueprint Editor.
- Re-run Blueprint Insights after save.

### 9.4 Reorder Exercises

MVP:

- Move up/down controls per exercise.
- Grouped technique rows move together.

Post-launch:

- Drag and drop reorder.

### 9.5 Move Workout Day

Entry:

- Day card action or day detail action: `Move`

Modal:

- Select target week/day
- Show conflict if target already has training
- Options:
  - Swap days
  - Move and make original rest
  - Cancel

Validation:

- Re-run Program Insights after move.

### 9.6 Modify Progression

MVP:

- Week-level progression notes editor.
- Day-level progression notes editor.

Post-launch:

- Structured progression editor:
  - Load progression
  - Volume progression
  - Rep progression
  - RPE progression
  - Deload week

## 10. Approval UX

Approval must be explicit and irreversible enough to deserve a confirmation step.

### 10.1 Approval CTA

Primary CTA:

- `Approve Draft`

Disabled when:

- Any blocker remains
- Generation is incomplete
- Kynovant Insights audit failed
- Draft has stale edits not yet validated

Warnings state:

- If warnings exist, CTA opens acknowledgement modal.

### 10.2 Approval Modal

Title:

- `Approve generated Program?`

Summary:

- Program name
- Client or Library Program
- Weeks
- Training days per week
- Number of Blueprints to create
- Warning count
- Blocker count

Required checkbox:

- `I have reviewed this draft and approve creating these Program and Blueprint records.`

Actions:

- `Cancel`
- `Create Program and Blueprints`

### 10.3 Create Program and Blueprints

Behavior:

- Creates ordinary draft Program Template record.
- Creates ordinary draft or active Blueprint records according to chosen approval setting.
- Links Program week/day slots to created Blueprints.
- Stores generator audit metadata.
- Does not publish unless coach selected `Create as published` and all validations allow it. MVP should default to draft.

Recommended MVP:

- Always create Program and Blueprints as draft.
- Coach publishes through existing manual workflow.

### 10.4 Optional Client Assignment

If a client is selected:

- After creation, success screen offers:
  - `Assign to Client`
  - `Open Program`
  - `Review Blueprints`

Assignment behavior:

- Uses existing Assign Program flow.
- Requires explicit coach confirmation.
- Does not automatically replace active Program.

If no client is selected:

- Success screen offers:
  - `Open Program`
  - `Assign Later`
  - `Create Another`

## 11. Success State

Success screen:

- Title: `Program draft created`
- Body: `The Program and Blueprints are now available in HQ as drafts.`
- Created assets:
  - Program name
  - Blueprint count
  - Week count
  - Client, if selected
- Actions:
  - `Open Program`
  - `Review Blueprints`
  - `Assign to Client` if client selected
  - `Generate Another`

No celebratory exaggeration. Keep it operational.

## 12. Versioning and Audit Visibility

Every generated draft needs visible audit metadata.

### 12.1 Draft Header Metadata

Show compact:

- `Generated by Kynovant`
- Generated timestamp
- Draft version
- Validation state

Example:

`Generated by Kynovant · Aug 3, 2026, 1:42 PM · Draft v3 · Warnings`

### 12.2 Audit Drawer

Open from header: `View Audit`

Sections:

- Generation metadata:
  - draft ID
  - model/provider identifier if allowed internally
  - generated at
  - generated by coach ID
  - source client ID if present
  - prompt/brief version
- Brief snapshot:
  - structured fields
  - freeform instructions
  - excluded exercises
- Coach edits:
  - timestamp
  - actor
  - action type
  - affected entity
  - before/after summary
- Validation:
  - last Insights run
  - Program audit status
  - Blueprint audit statuses
  - blockers/warnings count

MVP:

- Metadata and edit log visible.

Post-launch:

- Full before/after diff per edit.
- Restore previous draft version.
- Compare generated versions.

- Entry point from Client workspace
- Program Brief form
- Generation progress state
- Safe failure / retry
- Draft Review route
- Weekly calendar
- Day/Blueprint detail

- Blueprint-level Kynovant Insights for selected day
- Warning/blocker distinction
- Manual edits to prescriptions
- Manual exercise replacement

- Explicit approval modal
- Create Program and Blueprint draft records

### MVP Should Not Include

- Autonomous assignment
- Autonomous publishing
- Client-visible generated drafts
- AI chat refinement loop

- Claims that Kynovant is optimizing outcomes

## 15. Required Backend API and Data Contracts

The UI will require the following backend contracts. Names are proposed and should align with existing `/api/internal/...` conventions.

### 15.1 Create Generation Draft

Endpoint:

`POST /api/internal/program-generator/drafts`

Purpose:

- Validate Program Brief.
- Create generation job and draft container.
- Return draft/job ID.

Request:

```ts
interface CreateProgramGenerationDraftRequest {
  clientId?: string;
  brief: ProgramGenerationBrief;
}
```

Response:

```ts
interface CreateProgramGenerationDraftResponse {
  ok: true;
  draftId: string;
  jobId: string;
  status: "queued" | "running";
}
```

### 15.2 Program Brief Contract


### 15.8 Run Insights

Endpoint:

`POST /api/internal/program-generator/drafts/[draftId]/insights`

Purpose:

- Run deterministic Kynovant Insights against the generated draft.
- Return Program and Blueprint findings without persisting real Program records.

Response:

```ts
interface GeneratedDraftInsights {
  overallState: "ready" | "warnings" | "blocked" | "failed";
  blockers: DraftInsightFinding[];
  warnings: DraftInsightFinding[];
  cautions: DraftInsightFinding[];
  info: DraftInsightFinding[];
  programAudit: ProgramAuditResult;
  blueprintAudits: Record<string, BlueprintAuditResult>;
  dataQuality: DraftInsightFinding[];
  lastRunAt: string;
}
```

### 15.9 Approve Draft

Endpoint:

`POST /api/internal/program-generator/drafts/[draftId]/approve`

Request:

```ts
interface ApproveGeneratedProgramDraftRequest {

  acknowledgedWarningIds: string[];

```


### 15.10 Audit Metadata Contract

```ts
interface ProgramGenerationAudit {

    label: string;

  model?: {
    provider: string;
    model: string;

  briefVersion: number;
  sourceClientId?: string;
  edits: ProgramGenerationEditEvent[];
  validations: ProgramGenerationValidationEvent[];
}

interface ProgramGenerationEditEvent {
  id: string;
  createdAt: string;
  actorUserId: string;
  action:
    | "brief_updated"
    | "day_regenerated"
    | "exercise_replaced"
    | "prescription_updated"
    | "exercise_reordered"
    | "day_moved"
    | "progression_updated";
  entityType: "program" | "week" | "day" | "blueprint" | "prescription";
  entityId: string;
  summary: string;
}

interface ProgramGenerationValidationEvent {
  id: string;
  createdAt: string;
  status: "ready" | "warnings" | "blocked" | "failed";
  blockerCount: number;
  warningCount: number;
}
```

## 16. Data Storage Requirements

MVP likely requires new draft tables or equivalent JSONB storage:

- `program_generation_drafts`
- `program_generation_jobs`
- `program_generation_edit_events`
- `program_generation_validation_events`

Draft records should store generated content separately from real Program and Blueprint tables until approval.

Approval transaction must:

1. Verify draft belongs to authorized coach scope.
2. Verify validation state is approvable.
3. Create workout templates.
4. Create workout sections and prescriptions.
5. Create program template.
6. Create program weeks and day slots.
7. Link day slots to created workout templates.
8. Mark draft approved.
9. Store created record IDs.

If any step fails, the transaction rolls back.

## 19. Implementation Notes

- Build the UI as additive routes/components.
- Do not alter existing Program Builder or Blueprint Editor behavior.
- Use existing manual editors as the escape hatch for detailed editing after approval.
- Keep generation draft state separate from real Program/Blueprint records.
- Make validation and approval server-authoritative.
- Treat Kynovant Insights as deterministic validation, not generation.
- Prefer explicit coach actions over background automation.
